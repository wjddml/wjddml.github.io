커널 익스 자료는 대개 두 종류다. 취약점을 터뜨리는 방법과 할당자를 요리하는 방법. 그런데 막상 해보면 막히는 자리는 그 사이가 아니라 **그 다음**이다. 제어권은 잡았는데 링 3으로 어떻게 돌아가는지, 왜 복귀 직후에 죽는지, 왜 어떤 환경에서는 똑같은 코드가 멈춘 것처럼 보이는지.

그 구간은 리눅스 자료구조의 영역이 아니라 CPU 인터페이스의 영역이다. 커널 소스를 읽어도 안 나오고, 대신 Intel SDM이 "이 조건을 만족시켜라"라고 적어둔 쪽에 있다. 여기서는 그 조건만 모았다.

시작점으로 쓸 만한 사실이 하나 있다. 리눅스의 `struct pt_regs` 상위 다섯 칸이 `iretq`가 요구하는 스택 프레임과 **정확히 같은 레이아웃**이다. 진입할 때 쌓는 것과 나갈 때 꺼내는 것이 같은 모양이라는 뜻이고, 이 글의 내용 대부분이 거기서 따라온다.

## 1. 레지스터

### CS — 권한은 여기 2비트다

CPL은 별도 레지스터가 아니다. **현재 CS 셀렉터의 하위 2비트**가 그대로 권한 레벨이다. 커널 익스에서 "권한 상승"의 CPU 쪽 정의는 이 2비트를 3으로 되돌리면서 나머지 상태를 모순 없이 맞추는 일이다.

리눅스 x86-64가 쓰는 값은 네 개뿐이다. 익스에 상수로 박아넣을 값이 아니라, 레지스터 덤프를 보고 지금 어느 쪽에 있는지 알아보기 위한 참조표로 쓴다.

```
__KERNEL_CS   0x10      index 2, RPL 0
__KERNEL_DS   0x18      index 3, RPL 0
__USER_DS     0x2b      index 5, RPL 3
__USER_CS     0x33      index 6, RPL 3
```

`0x33 = (6 << 3) | 3`이다. 상위 비트가 GDT 인덱스, 하위 2비트가 RPL.

CS 디스크립터에는 L 비트가 하나 더 있어서 64비트 모드와 compatibility mode를 가른다. CS를 "권한 2비트짜리 필드"로만 보면 안 되는 이유다. 다만 복귀에 쓸 CS는 상수로 정하는 게 아니라 진입 전에 저장해둔 값을 그대로 되돌리므로, 실무에서 L 비트까지 들어갈 일은 거의 없다.

### SS — CS와 짝을 맞춰야 한다

`iretq`는 SS의 RPL이 복귀하려는 CPL과 맞는지 검사한다. CS에 `0x33`을 넣고 SS에 커널 값을 남겨두면 복귀 자체가 `#GP`로 끝난다. 둘은 항상 같이 세팅한다.

DS·ES는 64비트 모드에서 base와 limit이 무시되므로 사실상 신경 쓸 게 없다. FS·GS만 다르다 — 이 둘은 base를 MSR로 따로 갖는다.

### RFLAGS — IF를 빼먹으면 멈춘 것처럼 보인다

복귀 프레임에 넣는 RFLAGS에 IF(인터럽트 enable)가 꺼져 있으면, 유저 코드로는 정상 복귀하지만 그 뒤로 타이머 인터럽트가 안 들어온다. 크래시가 아니라 **정지**로 보이기 때문에 원인 찾기가 성가시다.

그래서 익스는 거의 항상 진입 전에 자기 RFLAGS를 저장해두고 그대로 되돌린다.

AC 비트(18번)도 알아둘 가치가 있다. 이 비트가 서 있으면 SMAP 검사가 통과된다. 링 0에서 `stac`을 실행하거나 RFLAGS를 통째로 제어할 수 있으면 SMAP이 사실상 꺼진다.

### CR 레지스터 — 읽을 수는 없지만 알아야 한다

유저랜드에서 직접 읽을 방법이 없다. 그래도 어떤 비트가 무엇을 막는지는 알아야 기법 선택이 된다.

```
CR0.WP    bit 16    쓰기 보호. 끄면 .rodata 수정 가능
CR3                 페이지 테이블 루트. KPTI 우회의 핵심
CR4.PCIDE bit 17    PCID. KPTI 성능 보전용이고 CR3 조작 시 비트 처리 주의
CR4.SMEP  bit 20    링 0에서 유저 페이지 실행 금지
CR4.SMAP  bit 21    링 0에서 유저 페이지 접근 금지
```

CR4로 SMEP·SMAP을 꺼버리는 고전 기법은 요즘 커널에서 잘 안 된다. `native_write_cr4`가 핀 걸린 비트를 검사해서 되돌리기 때문이다. 명령어 차원에서 `mov cr4`를 직접 실행할 수 있다면 여전히 유효하지만, 커널 함수를 호출해서 바꾸는 경로는 막혔다.

### MSR — 진입점이 여기 적혀 있다

```
IA32_LSTAR          0xc0000082    syscall 진입 RIP
IA32_STAR           0xc0000081    syscall이 적재할 CS·SS
IA32_FMASK          0xc0000084    syscall 진입 시 지울 RFLAGS 비트
IA32_GS_BASE        0xc0000101    현재 GS base
IA32_KERNEL_GS_BASE 0xc0000102    swapgs가 교환할 상대편
```

`IA32_LSTAR`를 덮는 것이 syscall 후킹이고, GS base 두 개가 `swapgs`의 양쪽이다. 커널은 GS base로 per-cpu 영역을 가리키고, 유저랜드는 TLS를 FS로 쓴다. **이 비대칭이 뒤에 나오는 디버깅 함정의 원인이다.**

## 2. 메모리와 구조체

### iretq 프레임 — 5칸, 이 순서

링 0에서 유저로 돌아가는 표준 경로다. `iretq` 실행 시점의 RSP가 가리키는 곳부터 위로:

```
rsp + 0x00    RIP        돌아갈 유저 코드
rsp + 0x08    CS         저장해둔 유저 CS
rsp + 0x10    RFLAGS     저장해둔 값. IF 포함
rsp + 0x18    RSP        유저 스택
rsp + 0x20    SS         저장해둔 유저 SS
```

64비트 모드의 `iretq`는 권한이 바뀌든 안 바뀌든 **항상 다섯 개를 다 꺼낸다**. 32비트 시절처럼 같은 권한일 때 RSP·SS를 생략하는 동작이 없다.

순서를 외우는 게 번거로우면, 진입할 때 커널이 쌓는 것과 같다고 기억하면 된다.

### pt_regs — 공격자 값이 커널 스택에 그대로 남는다

syscall이나 인터럽트로 커널에 들어오면 엔트리 코드가 유저 레지스터를 커널 스택 최상단에 고정 레이아웃으로 쌓는다. 낮은 주소부터:

```
r15 r14 r13 r12 rbp rbx r11 r10 r9 r8 rax rcx rdx rsi rdi orig_rax
rip cs eflags rsp ss
```

뒤의 다섯 개가 방금 본 `iretq` 프레임이다.

앞의 열여섯 개가 더 중요하다. **전부 유저가 정한 값이고, 커널 스택의 알려진 오프셋에 놓인다.** 레지스터 하나하나에 원하는 값을 넣고 syscall을 부르면 커널 스택에 그 값들이 깔린다. 누출 없이 확보되는 데이터이고, 스택 피벗 재료로 바로 쓸 수 있다.

위치는 `task->stack + THREAD_SIZE - sizeof(struct pt_regs)`다. 전환 기구 자체가 공격 자원이 되는 지점이고, RetSpill 논문이 이 성질을 체계화했다.

### TSS — RSP0와 IST

롱 모드의 TSS는 태스크 전환용이 아니다. 두 가지만 들고 있다.

```
RSP0        인터럽트·예외로 링 0에 진입할 때 적재할 스택
IST[1..7]   특정 벡터가 강제로 쓸 스택 (NMI, #DF, #DB 등)
```

여기서 갈리는 점 하나. **인터럽트·예외는 TSS.RSP0으로 스택을 바꾸지만, `syscall`은 스택을 바꾸지 않는다.** `syscall`은 RSP를 건드리지 않고 그냥 RIP만 `IA32_LSTAR`로 던진다. 커널 스택 적재는 엔트리 코드가 per-cpu에서 손으로 가져오는 소프트웨어 작업이다.

TSS.RSP0을 덮으면 다음 인터럽트가 공격자가 정한 주소를 커널 스택으로 쓴다.

### 페이지 테이블 비트 — 세 개면 된다

```
bit 0     P      present
bit 2     U/S    1이면 유저 접근 가능
bit 63    NX     실행 금지
```

SMEP·SMAP의 판정 기준이 U/S 비트다. 링 0에서 U/S=1인 페이지를 실행하려 하면 SMEP이, 읽거나 쓰려 하면 SMAP이 막는다. 둘 다 `#PF`로 나타난다.

## 3. 명령어

```
syscall     RCX ← RIP, R11 ← RFLAGS, RIP ← LSTAR, CS·SS ← STAR,
            RFLAGS &= ~FMASK.  RSP는 그대로 둔다
sysretq     RIP ← RCX, RFLAGS ← R11.  제약이 많아 익스에서는 잘 안 쓴다
iretq       위의 5칸을 꺼내 복귀.  표준 경로
swapgs      IA32_GS_BASE ↔ IA32_KERNEL_GS_BASE.  경계마다 정확히 한 번
stac/clac   RFLAGS.AC 설정·해제.  SMAP 우회 그 자체
mov crN     CR3 교체(KPTI), CR4 조작(SMEP·SMAP)
rdmsr/wrmsr LSTAR 후킹, GS base 조작
rdgsbase    CR4.FSGSBASE가 켜져 있으면 유저랜드에서도 GS base 조작 가능
pushfq/popfq 유저 RFLAGS 저장·복원
```

복귀 코드는 결국 이 두 줄로 끝난다.

```asm
swapgs
iretq
```

KPTI가 켜져 있으면 이 두 줄로는 안 된다. 커널 CR3에 유저 주소가 매핑되어 있지 않아서 `iretq` 직후 바로 폴트가 난다. CR3를 직접 갈아끼우거나, 커널이 이미 갖고 있는 복귀 트램폴린 `swapgs_restore_regs_and_return_to_usermode`를 빌려 쓴다.

트램폴린은 앞부분이 `pop` 열거라서 심볼 주소부터 통째로 쓰면 스택을 과하게 먹는다. 건너뛰고 `mov %rsp, %rdi` 지점으로 바로 들어간다.

그 지점 이후 코드가 하는 일을 보면 필요한 프레임이 그대로 나온다. 옛 RSP를 `%rdi`에 옮겨두고, 그것을 기준으로 일곱 칸을 읽어 새 스택에 다시 쌓고, CR3를 유저 쪽으로 바꾼 뒤 `pop %rdi`·`pop %rsp`를 하고 `iretq`로 간다. 그래서 진입 시점의 스택은 이렇게 생겨야 한다.

```
+0x00   RDI      트램폴린이 pop해 갈 자리
+0x08   RAX      같음
+0x10   RIP
+0x18   CS
+0x20   RFLAGS
+0x28   RSP
+0x30   SS
```

앞의 두 칸이 "더미 두 개"로 알려진 것의 정체다. 버려지는 패딩이 아니라 트램폴린이 `%rdi`와 `%rax`로 복원할 슬롯이다. 값이 무의미한 이유는 복귀 직후 유저 코드가 그 둘을 덮어쓰기 때문이다.

진입 오프셋은 커널 빌드마다 달라지므로 상수로 적지 않는다. 심볼 주소를 받아 직접 디스어셈블해서 `mov %rsp, %rdi`까지의 거리를 구한다.

```bash
grep swapgs_restore_regs_and_return_to_usermode /proc/kallsyms
```

```
(gdb) x/40i <심볼 주소>
```

구한 거리를 익스 쪽 상수 하나로 두고, 커널이 바뀌면 그 값만 다시 재면 된다.

## 4. 틀렸을 때 어디서 죽는지

실제로 시간을 가장 많이 잡아먹는 표다.

| 실수 | 증상 |
|---|---|
| CS가 유저 CS가 아님 | `iretq`에서 `#GP`. 또는 CPL이 0으로 남아 유저 코드가 링 0에서 돌다 첫 접근에 폴트 |
| SS를 CS와 안 맞춤 | `iretq`에서 `#GP` |
| RFLAGS.IF 미설정 | 복귀는 성공. 그 뒤 인터럽트가 안 와서 **정지로 보임** |
| 5칸 순서 틀림 | `#GP`, 또는 엉뚱한 RIP로 점프해 설명 안 되는 크래시 |
| `swapgs` 누락 | **즉시 안 죽는다.** 유저 TLS는 FS라 한동안 멀쩡하고, GS를 쓰는 라이브러리 코드에 가서야 이상하게 죽는다 |
| `swapgs` 두 번 | 커널 per-cpu 포인터가 유저 GS에 남아, 다음 커널 진입이 쓰레기 base를 쓴다 |
| KPTI 켜진 채 생 `iretq` | 복귀 직후 `#PF` → 보통 더블 폴트나 패닉 |
| 트램폴린 오프셋 틀림 | `pop` 개수가 안 맞아 스택이 밀린 채 `iretq` 실행. 랜덤해 보이는 크래시 |
| 유저 메모리에 ROP 체인, SMAP 켜짐 | 링 0에서 읽는 순간 `#PF` |
| 유저 함수로 `ret`, SMEP 켜짐 | 실행 시점에 `#PF` |

아래 세 줄은 성격이 다르다. `swapgs` 누락과 트램폴린 오프셋 오류는 **증상이 원인에서 멀어서** 디버깅이 오래 걸린다. 복귀 직후가 아니라 한참 뒤에 터지면 이 둘을 먼저 의심한다.

## 5. 지금 무엇이 켜져 있는지

기법 선택이 전부 여기서 결정되므로 가장 먼저 확인한다.

```bash
grep -o 'smep\|smap\|pti\|pcid' /proc/cpuinfo | sort -u
dmesg | grep -i 'page table isolation\|smep\|smap'
cat /sys/devices/system/cpu/vulnerabilities/meltdown
```

연습 환경이면 QEMU 실행 스크립트를 보는 게 더 빠르다. 켜고 끄는 자리가 거기다.

```
-cpu qemu64,+smep,+smap
-append "... nopti nokaslr"
```

`+smep,+smap`을 떼면 유저 메모리를 자유롭게 쓸 수 있고, `nopti`를 넣으면 `swapgs; iretq` 두 줄로 복귀가 끝난다. 처음에는 전부 끄고 복귀 경로만 맞춰본 다음, 하나씩 켜면서 어떤 단계가 추가로 필요해지는지 보는 순서가 좋다.

## 유저 상태 저장

복귀 프레임의 네 값은 진입 전에 저장해두는 게 정석이다.

```c
unsigned long user_cs, user_ss, user_rsp, user_rflags;

void save_user_state(void)
{
	__asm__ volatile(
		"movq %%cs,  %0\n"
		"movq %%ss,  %1\n"
		"movq %%rsp, %2\n"
		"pushfq\n"
		"popq %3\n"
		: "=r"(user_cs), "=r"(user_ss), "=r"(user_rsp), "=r"(user_rflags)
		:
		: "memory"
	);
}
```

셀렉터 값을 상수로 박으면 커널 설정이 다른 환경에서 원인이 안 보이는 `#GP`로 나타난다. 앞의 표는 덤프를 읽을 때 쓰는 참조용이고, 복귀 프레임에 실제로 넣는 값은 항상 여기서 저장한 것을 쓴다.

## 정리

트리거 이후 구간에서 CPU가 요구하는 것은 결국 네 가지다.

**CS·SS를 짝 맞춰 링 3 값으로.** 권한은 CS 하위 2비트고 `iretq`가 SS와의 일관성을 검사한다.

**5칸 프레임을 정확한 순서로.** `pt_regs` 상위 5칸과 같은 레이아웃이다.

**`swapgs`를 경계마다 정확히 한 번.** 누락과 중복 둘 다 증상이 늦게 나타난다.

**CR3를 유저 쪽으로.** KPTI가 켜져 있을 때만 필요하고, 직접 바꾸거나 커널 트램폴린을 빌린다.
